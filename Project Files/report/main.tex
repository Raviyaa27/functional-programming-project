\section{Introduction and How to Run}
%=============================================================================
This report describes a small, type-safe arithmetic expression interpreter
in Haskell~\cite{hutton2016programming}, covering Parts A--E of the
assignment. Every module compiles without warnings under GHC~9.6.7 with
\code{-Wall}. Only \code{cabal test} needs more than GHC (it downloads
QuickCheck).
\begin{lstlisting}[style=plain]
git clone https://github.com/Raviyaa27/functional-programming-project
cd "functional-programming-project/Project Files/haskell"
runghc Main.hs     # demo: samples, simplify, batch report
runghc Tests.hs    # 72 expected-vs-actual unit tests
cabal test         # the unit tests and 8 QuickCheck properties
python ../imperative/imperative_eval.py    # Part D (Python 3.10+)
\end{lstlisting}

\section{Design and Implementation}\label{sec:design}
%=============================================================================
\subsection{Language Design (Part A)}
\begin{lstlisting}[style=hs, numbers=none, xleftmargin=0pt, framexleftmargin=0pt,
  caption={The types of Part A (abridged from \code{Expr.hs}, lines 47--72).},
  label=lst:types]
data Expr  = Lit Double | Var String
           | Add Expr Expr | Sub Expr Expr | Mul Expr Expr | Div Expr Expr
           | Let String Expr Expr            -- let x = e1 in e2
           | If BExpr Expr Expr              -- if b then e1 else e2
data BExpr = BLit Bool | Less Expr Expr | Equal Expr Expr
           | And BExpr BExpr | Or BExpr BExpr | Not BExpr
type Env   = [(String, Double)]
\end{lstlisting}
\code{Expr} is a sum type with eight alternatives, each carrying exactly the
fields it needs: besides the six required constructors, \code{Let} adds a
local binding and \code{If} a choice. Conditions have their own type,
\code{BExpr}, so numbers and conditions cannot be mixed. In an \code{Env},
\code{lookup} finds the first match, so new bindings shadow old ones.

\subsection{Evaluation (Part B)}
\lstinputlisting[style=hs, firstline=84, lastline=102, firstnumber=84,
  caption={The evaluator (\code{Expr.hs}, lines 84--102).},
  label=lst:eval]{../haskell/Expr.hs}
\code{eval} has one equation per constructor and recurses on the
sub-expressions. Errors are values of type \code{Either String Double}: the
arithmetic cases use applicative style and \code{Div}, \code{Let} and
\code{If} use \code{do}-notation in the \code{Either}
monad~\cite{wadler1995monads}, so the first \code{Left} stops evaluation and
becomes the result. An undefined variable (line~86) and division by zero
(lines 91--96) are reported this way, never as exceptions. The mutually
recursive \code{evalB} (lines 106--116) evaluates conditions with
short-circuiting \code{And}/\code{Or}, and \code{If} evaluates only the chosen
branch.

\subsection{Simplification and Higher-Order Functions (Part C)}
\code{simplify = rewrite . descend} (lines 133--168) simplifies the children
first and then applies the first matching rule at the root: nine identities
($x+0$, $0+x$, $x-0$, $x-x$, $x \cdot 1$, $1 \cdot x$, $x \cdot 0$,
$0 \cdot x$, $x/1$), constant folding (never of $n/0$, which \code{eval} must
report), \code{if} with a constant condition, and removal of an unused
\code{let}; \code{simplifyB} adds double negation and constant comparisons.
Being bottom-up, one pass reaches a normal form, e.g.\
\code{x * 1 + 0}~$\to$~\code{x}.
\lstinputlisting[style=hs, numbers=none, xleftmargin=0pt, framexleftmargin=0pt,
  linerange={204-205,209-209,221-222,224-227},
  caption={The list functions (excerpt of \code{Expr.hs}, lines 204--227).},
  label=lst:hof]{../haskell/Expr.hs}
\code{eval env} is a partially applied (curried) function
\code{Expr -> Either String Double} that \code{map} applies to each expression
(line~205). \code{evalBatch} composes it with \code{rights}, \code{batchReport}
counts successes and failures in one \code{foldr} (6 and 3 on the samples),
and \code{undefinedVars} uses \code{filter} with the section
\code{(\textasciigrave notElem\textasciigrave{} bound)} (line~257) to find unbound variables statically.

\textbf{Errors.} In Haskell, failure is part of the type of \code{eval}, so
a caller must handle the \code{Left} before using the \code{Double}, and
\code{<*>} and \code{do} propagate it at no cost. In Python, failure is
invisible in the signature and a forgotten \code{except} crashes the
program.
\textbf{State.} Python reassigns \code{result} in every case and overwrites the
shared \code{env} in \code{let}; without the \code{finally}, an error in a
\code{let} body would leave the binding behind. Haskell has no mutable state.
\textbf{Bugs ruled out.} \code{imperative\_eval.py} runs five programs that
GHC rejects before they run (the last rows of Table~\ref{tab:compare}, plus a
string literal that crashes with \code{TypeError}). Division by zero and
unbound variables depend on run-time values, so neither version excludes them
by types; Haskell returns them as values instead of throwing them.

\section{Reflection (Part E)}\label{sec:reflect}
%=============================================================================
\textbf{Pure functions.} A pure function's result depends only on its
arguments, and it has no side effects. The type of \code{eval} (line~84) has
no \code{IO}, so it cannot print, read input or change any variable; the same
environment and expression always give the same result, and likewise for
\code{simplify}. This made testing simple: a unit test just compares values,
and QuickCheck can compare \code{eval env e} with
\code{eval env (simplify e)} thousands of times. Functions are also values:
\code{eval env} is passed to \code{map} (line~205)~\cite{hughes1989why}.

\textbf{Immutability.} Nothing is updated in place. Line~99,
\code{eval ((x, v) : env) body}, does not modify \code{env}: it builds a new
list whose tail \emph{is} the old one (shared, not copied). When the
\code{let} ends, the caller still holds its original \code{env}, so the
binding disappears with no clean-up (sample~4) and Python's
\code{try}/\code{finally} has no counterpart. \code{simplify} likewise builds a
new tree (lines 140--145) and leaves its input intact, so \code{Main.hs}
prints each expression before and after simplification from the same value.

\textbf{Why invalid expressions cannot be constructed.} Each constructor fixes
the number and types of its fields: \code{Add} takes exactly two \code{Expr}s,
and \code{If} takes a \code{BExpr} and two \code{Expr}s. An operator with a
missing operand, or a misspelt one such as \code{Mull}, is therefore not an
\code{Expr} at all, and keeping conditions in a separate type turns Python's
silent bugs into compile errors (\code{compile\_errors.txt}):
\begin{lstlisting}[style=plain]
bad1 = If (Lit 1) (Lit 2) (Lit 3)
  * Couldn't match expected type `BExpr' with actual type `Expr'
\end{lstlisting}
\code{Add (Less (Lit 1) (Lit 2)) (Lit 3)} fails likewise with the types
swapped, and a function that forgets a constructor gets a warning naming it
(\code{Patterns of type \textasciigrave Expr\textquotesingle{} not matched: If \_ \_ \_}). Errors that depend
on values (an unbound name, a zero divisor) are beyond the types; \code{eval}
returns them as \code{Left}, and \code{undefinedVars} finds unbound names
before evaluation (QuickCheck confirms it is sound and complete).
\code{TypedExpr.hs} goes further with a GADT indexed by the result type, so a
single expression type still rejects ill-typed terms at compile time.

\textbf{What testing revealed.} QuickCheck refuted the claim that
\code{simplify} never changes whether evaluation succeeds by finding
\code{w - w}: it fails with \code{undefined variable: w} but simplifies to
\code{0}, because rules that discard a sub-expression ($x \cdot 0$, $x - x$,
an unused \code{let}) discard its error too. What holds, on 1000 random
expressions, is that every \emph{successful} result is preserved; because
failure is a value, this was visible and testable.
